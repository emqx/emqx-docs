# ネームスペース

EMQX 5.9.0 以降、ネームスペース機能により、ユーザーは MQTT クライアントを論理的にグループ化し、単一の EMQX クラスター内でトラフィック制限を適用できるようになりました。この機能は、複数のクライアントグループ（事業部門、アプリケーション、顧客など）が同じインフラを共有しつつ、論理的に分離されたスケーラブルなデプロイメントを可能にします。

EMQX のネームスペース機能は以下の2つの部分で構成されています。

- **MQTT クライアントネームスペース** — MQTT クライアントを（ユーザー名、SNI、その他の接続メタデータによって）論理的にグループ化し、ネームスペースごとのクォータ、レート制限、クライアントIDおよびトピックの分離設定を適用します。
- **管理ユーザーネームスペース** — ダッシュボード、CLI、API ユーザーを [namespaced roles](../dashboard/system.md/#namespaced-roles) により特定のネームスペースにスコープし、委任された管理者が割り当てられたネームスペース内のリソースのみを閲覧・操作できるようにします。EMQX 6.0 以降で利用可能です。

::: warning 信頼されたデプロイメントのみ

**管理ユーザーネームスペース** は、組織内のチームや事業部門を分離するなど、信頼された内部デプロイメント向けに設計されています。誤って互いの設定を変更してしまうリスクを減らす目的であり、強力な分離保証やパブリック・非信頼型マルチテナントデプロイメントのセキュリティ境界を提供するものではありません。パブリックなマルチテナント環境で管理ユーザーネームスペースを検討されている場合は、EMQ の営業担当にご相談ください。このユースケースは現時点で標準機能としてサポートされていません。

**MQTT クライアントネームスペース** に関しては、ネームスペース間のクライアント分離はオプトインであり、明示的な設定が必要です。ネームスペース間のクライアントが相互に信頼されていない場合は、[分離メカニズム](#isolation-mechanisms) を参照し、クライアントIDのオーバーライドやトピックマウントポイントの設定を行ってください。

:::

## ネームスペースとは

EMQX Enterprise のネームスペースは、MQTT クライアントの論理的分離とリソース管理のための仕組みです。異なる事業部門やテナントのクライアントを共有クラスター内で別々のネームスペースに分割し、接続、メッセージ、クォータなどの分離を実現します。

ネームスペースは特別なクライアント属性 `tns`（テナントネームスペース）で識別され、ユーザー名や Server Name Indication（SNI）などのクライアント接続メタデータから抽出されます。

> **典型的なユースケース**：企業内の複数事業部門によるクラスター共有、テナント単位のリソース分離管理、集中アクセス制御など。

### ネームスペースで実現できること

- **クライアントおよびメッセージの論理的分離**

  ネームスペースにより、異なるテナント間でクライアントIDやトピックスペースを論理的に分離できます。

  ::: tip 補足

  ネームスペースを有効にしても、クライアントIDのオーバーライドやトピックプレフィックスは自動的に適用されません。これらは手動で設定する必要があります。詳細は [分離メカニズム](#isolation-mechanisms) をご覧ください。

  :::

- **テナント単位のクォータおよび接続制御**

  ネームスペースごとに同時接続数やメッセージパブリッシュレートの上限を設定でき、公平な利用とシステム安定性を確保します。

- **強化されたログおよび運用可視性**

  ログには自動的にネームスペース識別子（`tns`）が含まれ、クライアント活動の追跡や問題検出、テナント単位の診断が容易になります。

- **ネームスペースベースのリソース監視**

  ネームスペースはテナントごとの接続数やメッセージスループットなどのメトリクス収集の境界を提供し、キャパシティプランニングや運用インサイトに不可欠です。

- **管理ユーザーの分離**

  EMQX 6.0 以降、ネームスペースはダッシュボード、CLI、API ユーザーにも [namespaced roles](../dashboard/system.md/#namespaced-roles) を通じて拡張されました。信頼モデルや必要な安全対策については本ページ上部の [信頼されたデプロイメントのみ](#namespace) の注意事項を参照してください。

  - 管理ユーザーは特定のネームスペースに限定したロール（例：`ns:team_a::administrator`）で作成可能です。
  - ネームスペースユーザーは割り当てられたネームスペース内のリソースのみ閲覧・操作できます。
  - ネームスペース対応していないクラスター全体の設定は閲覧可能ですが読み取り専用で、変更はグローバル管理者のみ可能です。
  - これにより、データ分離と並行してテナント固有の安全な管理アクセスが実現します。

- **マルチテナント管理**

  システム管理者は同一クラスター内で複数のネームスペースを管理でき、各テナントは分離されたリソースとユーザー権限の自己完結型環境で運用可能です。

## 管理ユーザーネームスペースの運用セキュリティ

委任されたネームスペース管理者は、コネクター、ブリッジ、アクションなどのアウトバウンドターゲットを設定できます。追加の制御がなければ、内部や機密ネットワークへの意図しないアクセスを許してしまう可能性があります。

利用可能な場合は `rule_engine.ssrf` を有効にしてルールエンジン管理のアウトバウンドターゲットを検証してください。さらに、ランタイムのネットワーク制御が必要な場合は EMQX ホスト側で以下のイグレス制御を追加してください。

- アイデンティティプロバイダー（IdP）、Webhook、コネクターバックエンドなど承認済みの宛先へのみアウトバウンドアクセスを許可する。
- インスタンスメタデータサービス、ループバックアドレス、リンクローカルアドレス、内部管理ネットワークへのアクセスは明示的に必要な場合を除き拒否する。典型的なブロック対象メタデータエンドポイントは `100.100.100.200`、`169.254.169.253`、`169.254.169.254`、`fd00:ec2::254` などです。
- 新しい統合や管理機能でアウトバウンド HTTP/TCP 接続を開始する場合は、必ずファイアウォールルールを見直してください。

詳細は [ルールエンジンポリシーとファイアウォールルールによる SSRF 対策](../deploy/cluster/security.md#mitigate-ssrf-with-rule-engine-policy-and-firewall-rules) を参照してください。

## 分離メカニズム

EMQX は高い柔軟性を持ち、ネームスペース機能導入前から様々な分離方法をサポートしてきました。ネームスペース機能は統一されたテナント識別子フィールド（`client_attrs.tns`）を提供し、クライアントIDやトピックマウントポイントの設定をテナント情報に基づいて整理・管理できるようにします。

クライアントIDやトピックの分離は自動的には有効になりません。信頼モデルやビジネス要件に応じて手動で設定してください。EMQX 6.0.3 以降、ルールトリガーの分離はデフォルトで有効ですが、これは名前空間ルールをトリガーするメッセージやイベントを制限するものであり、クライアントIDやトピックの分離に代わるものではありません。

- **クライアントIDオーバーライド**

  ::: warning 信頼されていないマルチテナント環境で必須

  異なるネームスペースのクライアントが相互に信頼されていない場合（例：各ネームスペースが外部顧客や別組織を表す場合）、`mqtt.clientid_override` の設定が必須です。設定しないと、あるネームスペースのクライアントが他のテナントのクライアントIDを使い回し、接続を切断したり、永続セッションを乗っ取ったり、サービス拒否を引き起こしたりする可能性があります。認証はこれを防げません。セッションの乗っ取りは ACL 適用前の接続レイヤーで発生します。

  これに加えて [トピック分離のためのマウントポイント](#isolation-mechanisms) を設定し、トピックレベルでのアクセスがネームスペースを跨がないようにしてください。

  :::

  異なるネームスペースのクライアントが同じクライアントIDを使って EMQX に接続したい場合は、クライアントIDオーバーライドルールを設定できます。例：

  ```hocon
  mqtt.clientid_override = "concat([client_attrs.tns, '-', clientid])"
  ```

  このルールはクライアントIDの先頭にネームスペースを付加し、競合を回避します。

- **マウントポイントによるトピック分離**

  異なるネームスペースのクライアントが同じトピック名をパブリッシュ／サブスクライブしても互いに影響を与えないように、マウントポイントを使ってネームスペースプレフィックスを自動付加できます。

  ```
  listener.{TYPE}.{NAME}.mountpoint = "${client_attrs.tns}/"
  ```

  この設定により、トピック名にネームスペースのプレフィックスが付加されます。

- **ルールトリガー分離**

  `rule_engine.limit_selects_in_namespace` を有効にすると、ネームスペースに属するルールは同じネームスペースのクライアントからのメッセージやイベントによってのみトリガーされます。EMQX はクライアント属性 `client_attrs.tns` でクライアントのネームスペースを識別します。

  この設定は他のネームスペースからのメッセージやイベントによるルールトリガーを防止するだけで、クライアントのパブリッシュやサブスクライブを制限するものではありません。クライアントのトピックアクセスを分離するには、マウントポイントと認可ルールによるトピック分離を設定してください。

ネームスペース分離の現状と今後の計画については、[マルチテナンシーロードマップ](#multi-tenancy-roadmap) を参照してください。

## ネームスペースの有効化

ネームスペース機能を有効にするには、まず EMQX にクライアントがどのネームスペースに属するかを判定させる必要があります。これは特別なクライアント属性 `tns`（テナントネームスペース）を設定することで実現します。

### 設定ファイルによるネームスペース有効化

`tns` 属性は、クライアントの接続メタデータ（ユーザー名、SNI、その他のフィールド）から抽出できます。

例えば、クライアントのユーザー名をネームスペース識別子として使う場合、以下の設定を適用します。

```
mqtt.client_attrs_init = [{expression = username, set_as_attr = tns}]
```

### ダッシュボードによるネームスペース有効化

EMQX ダッシュボードからもネームスペースを有効にできます。

1. **管理** -> **MQTT 設定** -> **一般** タブに移動し、**クライアント属性** セクションを探します。
2. **追加** をクリックし、以下の情報を入力します。
   - **属性**：`tns`
   - **属性式**：例えばクライアントのユーザー名をネームスペース識別子にしたい場合は `username` を入力します。他の変数も利用可能です。属性式の詳細は [クライアント属性の設定](../client-attributes/client-attributes.md#set-client-attributes) を参照してください。
3. **変更を保存** をクリックします。

## マルチテナンシーロードマップ

以下の機能が段階的に展開されています。

- 管理ネームスペースと MQTT ネームスペースの統合
- 組み込みデータベース認証の分離実装
- 組み込みデータベース認可の分離実装
- 保持メッセージのクォータ分離実装
- Prometheus メトリクスの分離実装

::: tip アップデート

EMQX 6.0 以降、ルール、アクション、ソース、コネクターの分離は完全に実装され、ロードマップからは除外されています。

:::
