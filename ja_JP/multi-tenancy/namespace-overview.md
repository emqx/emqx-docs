# ネームスペース

EMQX 5.9.0以降、ネームスペース機能により、ユーザーはMQTTクライアントを論理的にグループ化し、単一のEMQXクラスター内でトラフィック制限を適用できるようになりました。この機能は、複数のクライアントグループ（事業部門、アプリケーション、顧客など）が同じインフラを共有しながら論理的に分離されたスケーラブルなデプロイメントを可能にします。

EMQXのネームスペース機能は以下の2つの部分で構成されています。

- **MQTTクライアントネームスペース** — MQTTクライアントをユーザー名、SNI、またはその他の接続メタデータで論理的にグループ化し、ネームスペースごとのクォータ、レート制限、およびクライアントIDやトピックの分離設定を適用します。
- **管理ユーザーネームスペース** — Dashboard、CLI、APIユーザーを[ネームスペースロール](../dashboard/system.md/#namespaced-roles)を通じて特定のネームスペースにスコープし、委任された管理者が割り当てられたネームスペース内のリソースのみを閲覧・操作できるようにします。EMQX 6.0以降で利用可能です。

::: warning 信頼されたデプロイメントのみ

**管理ユーザーネームスペース**は、同一組織内のチームや事業部門を分離するなど、信頼された内部デプロイメントを想定しており、誤ってお互いの設定を変更するリスクを減らすためのものです。強力な分離保証を提供せず、パブリックまたは信頼されていないマルチテナント環境のセキュリティ境界としては適していません。パブリックなマルチテナント環境で管理ユーザーネームスペースの利用を検討している場合は、EMQの営業にお問い合わせください。このユースケースは現時点で標準機能としてサポートされていません。

**MQTTクライアントネームスペース**に関しては、ネームスペース間のクライアント分離はオプトインであり、明示的な設定が必要です。ネームスペース間でクライアントが相互に信頼されていない場合は、[分離メカニズム](#isolation-mechanisms)を参照し、クライアントIDのオーバーライドやトピックマウントポイントの設定を行ってください。

:::

## ネームスペースとは

EMQX Enterpriseのネームスペースは、MQTTクライアントの論理的分離およびリソース管理のための仕組みです。異なる事業やテナントのクライアントを共有されたEMQXクラスター内で別々のネームスペースに分割し、接続、メッセージ、クォータなどの分離を実現します。

ネームスペースは、クライアントの接続メタデータ（ユーザー名やServer Name Indication（SNI）など）から抽出される特別なクライアント属性 `tns`（テナントネームスペース）で識別されます。

> **典型的なユースケース**：企業内の複数事業部門によるクラスター共有、テナント単位のリソース分離管理、集中アクセス制御など。

### ネームスペースで実現できること

- **クライアントとメッセージの論理的分離**

  ネームスペースにより、異なるテナント間でクライアントIDやトピックスペースを分離し、論理的に区分けできます。

  ::: tip 注意

  ネームスペースを有効にしても、クライアントIDのオーバーライドやトピックのプレフィックス付与は自動的には適用されません。これらは手動で設定する必要があります。詳細は[分離メカニズム](#isolation-mechanisms)を参照してください。

  :::

- **テナント単位のクォータと接続制御**

  ネームスペースごとに同時接続数やメッセージパブリッシュレートの制限を設定でき、公平な利用とシステムの安定性を確保します。

- **強化されたログと運用可視性**

  ログには自動的にネームスペース識別子（`tns`）が含まれ、クライアント活動の追跡、問題検出、テナント単位の診断が容易になります。

- **ネームスペースベースのリソース監視**

  ネームスペースはテナントごとの接続数やメッセージスループットなどのメトリクス収集の境界を提供し、キャパシティプランニングや運用の洞察に役立ちます。

- **管理ユーザーの分離**

  EMQX 6.0以降、ネームスペースはDashboard、CLI、APIユーザーにも[ネームスペースロール](../dashboard/system.md/#namespaced-roles)を通じて拡張されています。このページ上部の[信頼されたデプロイメントのみ](#namespace)の注意事項にある信頼モデルと必要な安全対策を参照してください。

  - 管理ユーザーは特定のネームスペースに限定したロール（例：`ns:team_a::administrator`）で作成可能です。
  - ネームスペースユーザーは割り当てられたネームスペース内のリソースのみを閲覧・操作できます。
  - ネームスペース未対応のクラスター全体設定は表示されますが、ネームスペースユーザーは読み取り専用で、変更はグローバル管理者のみ可能です。
  - EMQX 6.0.4以降、ネームスペース管理者は[自身のネームスペース内のAPIキーを管理可能](../admin/api.md#manage-api-keys-as-a-namespaced-administrator)です。グローバルキーや他ネームスペースのキーにはアクセスできません。
  - これにより、データ分離とともにテナント固有の安全な管理アクセスが保証されます。

- **マルチテナント管理**

  システム管理者は同一クラスター内で複数のネームスペースを管理でき、各テナントは独立した環境でリソースとユーザー権限を分離して運用できます。

## 管理ネームスペースの運用セキュリティ

委任されたネームスペース管理者は、コネクター、ブリッジ、アクションなどのアウトバウンドターゲットを設定可能です。追加の制御がないと、内部や機密ネットワークへの意図しないアクセスを許してしまう恐れがあります。

利用可能な場合は、`rule_engine.ssrf`を有効にして、コネクター設定のテスト、作成、更新時にHTTPおよびMQTTコネクターのターゲットを検証してください。EMQX 6.0.4以降、このポリシーは他のコネクタータイプやランタイム接続には適用されません。EMQXホスト側でアウトバウンドネットワーク境界を強制するために以下のような出口制御を追加してください。

- IdP、Webhook、コネクターバックエンドなど承認済みの宛先へのアウトバウンドアクセスのみ許可。
- インスタンスメタデータサービス、ループバックアドレス、リンクローカルアドレス、内部管理ネットワークへのアクセスは明示的に必要な場合を除き拒否。典型的なブロック対象のメタデータエンドポイントは `100.100.100.200`、`169.254.169.253`、`169.254.169.254`、`fd00:ec2::254` など。
- 新しい統合や管理機能でアウトバウンドHTTP/TCP接続を開始する場合は、必ずファイアウォールルールを見直してください。

詳細は[ルールエンジンポリシーとファイアウォールルールによるSSRF緩和](../deploy/cluster/security.md#mitigate-ssrf-with-rule-engine-policy-and-firewall-rules)を参照してください。

## 分離メカニズム

EMQXは高い柔軟性を持ち、ネームスペース機能導入前から様々な分離手法をサポートしてきました。ネームスペース機能は統一されたテナント識別子フィールド（`client_attrs.tns`）を提供し、クライアントIDやトピックマウントポイントの設定を統一されたテナント情報に基づいて整理・管理できるようにします。

クライアントIDやトピックの分離は自動的には有効になりません。信頼モデルやビジネス要件に応じて手動で設定してください。EMQX 6.0.3以降、ルールトリガーの分離はデフォルトで有効ですが、これは名前空間に属するルールをトリガーするメッセージやイベントを制限するものであり、クライアントIDやトピックの分離に代わるものではありません。

- **クライアントIDオーバーライド**

  ::: warning 信頼されていないマルチテナント環境で必須

  異なるネームスペースのクライアントが相互に信頼されていない場合（例えば各ネームスペースが外部顧客や別組織を表す場合）、`mqtt.clientid_override`の設定が**必須**です。これを設定しないと、あるネームスペースのクライアントが別のテナントのクライアントIDを使い回し、そのクライアントを強制切断したり、永続セッションを乗っ取ったり、サービス拒否を引き起こす可能性があります。認証はこれを防げません。セッション乗っ取りはACL適用前の接続レイヤーで発生します。

  [トピック分離のためのマウントポイント設定](#isolation-mechanisms)と組み合わせて、トピックレベルのアクセスもネームスペース間で交差しないようにしてください。

  :::

  異なるネームスペースのクライアントが同じクライアントIDを使いたい場合は、クライアントIDオーバーライドルールを設定できます。例：

  ```hocon
  mqtt.clientid_override = "concat([client_attrs.tns, '-', clientid])"
  ```

  このルールはクライアントIDにネームスペースをプレフィックスとして付加し、競合を回避します。

- **マウントポイントを使ったトピック分離**

  異なるネームスペースのクライアントが同じトピック名をパブリッシュ／サブスクライブしても互いに影響しないように、マウントポイントを使ってネームスペースのプレフィックスを自動付加できます。

  ```
  listener.{TYPE}.{NAME}.mountpoint = "${client_attrs.tns}/"
  ```

  この設定により、トピック名にネームスペースのプレフィックスが付与されます。

- **ルールトリガー分離**

  `rule_engine.limit_selects_in_namespace`を有効にすると、ネームスペースに属するルールは同じネームスペースのクライアントからのメッセージやイベントでのみトリガーされます。EMQXはクライアント属性`client_attrs.tns`でクライアントのネームスペースを識別します。

  この設定はルールのトリガー制限のみを行い、クライアントのパブリッシュやサブスクライブの制限は行いません。クライアントのトピックアクセスを分離するには、マウントポイントと認可ルールによるトピック分離を設定してください。

ネームスペース分離の現状と今後の計画については[マルチテナンシーロードマップ](#multi-tenancy-roadmap)を参照してください。

## ネームスペースの有効化

ネームスペース機能を有効にするには、まずEMQXにクライアントがどのネームスペースに属するかを判別させる必要があります。これは特別なクライアント属性`tns`（テナントネームスペース）を設定することで行います。

### 設定ファイルによるネームスペース有効化

`tns`属性は、クライアントの接続メタデータ（ユーザー名、SNI、その他のフィールド）から抽出できます。

例えば、クライアントのユーザー名をネームスペース識別子として使用する場合、以下の設定を適用します。

```
mqtt.client_attrs_init = [{expression = username, set_as_attr = tns}]
```

### ダッシュボードによるネームスペース有効化

EMQX Dashboardからもネームスペースを有効にできます。

1. **管理** -> **MQTT設定** -> **一般**タブの**クライアント属性**セクションに移動します。
2. **追加**をクリックし、以下の情報を入力します：
   - **属性**：`tns`
   - **属性式**：例としてクライアントのユーザー名をネームスペース識別子に使う場合は`username`を入力します。他の変数も使用可能です。属性式の詳細は[クライアント属性の設定](../client-attributes/client-attributes.md#set-client-attributes)を参照してください。
3. **変更を保存**をクリックします。
