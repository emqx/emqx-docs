# EMQX Enterprise Version 6

## 6.3.2

*リリース日: 2026-10-16*

### 強化点

#### コアMQTT機能

- [#19438](https://github.com/emqx/emqx/pull/19438) 混雑していない接続において、インメモリセッションは、以前のQoS 1/2メッセージがアックを待つ必要がある場合でも、キューに入ったQoS 0メッセージのドレインを楽観的に継続するようになりました。これは混雑が解消された後や既存のセッションが再開した場合のドレインも含みます。トピック優先度が有効な場合、QoS 0メッセージのドレインは早期に停止することがあります。

#### パフォーマンス

このリリースでは、MQTT接続、セッション、およびノードローカルクライアントデータのメモリ使用量を削減しました。また、複数のブローカーパスにおけるCPUオーバーヘッドを低減し、サブスクリプションの検索と起動パフォーマンスを向上させています。

- **接続とセッションのメモリ**
  - [#19092](https://github.com/emqx/emqx/pull/19092) 接続は `mqtt.hibernate_after`（デフォルト5秒間トラフィックなし）後にハイバネートします。ハイバネートによりプロセスヒープが使用中のデータに縮小され、接続ごとに約5KBのメモリを解放します。以前はTCP/TLS接続は `mqtt.idle_timeout`（デフォルト15秒）後にのみハイバネートし、WebSocket接続は最初のパケット送信後も起きたままでした。`mqtt.hibernate_after = infinity` に設定すると接続を起こしたままにできますが、クライアントがほぼその間隔で送信する場合は値を上げてください。ハイバネートごとにガベージコレクションが発生し、起床時にヒープが再成長するためです。
  - [#19181](https://github.com/emqx/emqx/pull/19181) ゾーンとリスナーでメッセージ、バイト、サブスクライブのレート制限が設定されていない接続は、レートリミッター状態を割り当てなくなりました。後から制限が設定されても既存接続に適用されます。
  - [#19262](https://github.com/emqx/emqx/pull/19262) キューにメッセージがないセッション（パブリッシュのみのクライアントや配信に追いついているサブスクライバーなど）は48バイトのメモリを節約します。
  - [#19563](https://github.com/emqx/emqx/pull/19563) Erlang/OTPを28.4.1-7に、`emqx-builder`を6.2-3にアップグレードしました。TLS接続は共有ソケットオプションのために接続ごとのETSテーブルを不要としメモリ使用量を削減し、アイドルTLS 1.3接続は暗号状態を解放します。TLSハンドシェイクは絶対パスの `cacertfile` 解決においてErlangファイルサーバーへの呼び出しを2回行わなくなり、TLS接続のバースト時のファイルサーバーのバックログを防止します。

- **ノードローカルクライアントデータ**
  - [#19306](https://github.com/emqx/emqx/pull/19306) channel-infoテーブルはクライアントのウィルメッセージ、CONNECTプロパティ、サブスクリプションリストを保存しなくなりました。エントリはCONNECTパケットやサブスクリプション数に応じて増加しなくなり、メモリ使用量とSUBACK/UNSUBACK後のテーブル書き換えコストを削減します。
  - [#19263](https://github.com/emqx/emqx/pull/19263) テーブルは `sockinfo` マップと、`conninfo` に既に含まれる `peerhost`、`peerport`、`peername`、`sockport` の値を削除し、接続ごとに約100バイトを節約します。
  - [#19303](https://github.com/emqx/emqx/pull/19303) 値が0のクライアント統計を保存しなくなり、アイドルクライアントごとに約145バイトを節約します。
  - [#19245](https://github.com/emqx/emqx/pull/19245) TCP、TLS、WebSocketでサブスクライブするクライアントはsubscriber-idテーブルに行を持たなくなり、クライアントごとに約110バイト、100万クライアントで約110MBを節約します。

  REST APIのレスポンス、CLI出力、フックコールバックの引数は変更ありません。`emqx_cm:get_chan_info/1,2`、`emqx_cm:lookup_client/1`、`emqx_mgmt:lookup_client/2`、`emqx_channel:info/1`、`emqx_connection:info/1`を通じてクライアント情報テーブルを直接読むプラグインは、返されるマップに `will_msg`、`conninfo.conn_props`、`session.subscriptions` を含みません。クライアントのサブスクリプションは `emqx_broker:subscriptions/1`、CONNECTプロパティは `client.connected` フック、単一属性の読み取りは `emqx_channel:info/2` を使用してください。

- **CPUとレイテンシ**
  - [#19527](https://github.com/emqx/emqx/pull/19527) メッセージ処理やクライアントライフサイクル操作中のフックは名前で直接呼び出されるようになりました。
  - [#19516](https://github.com/emqx/emqx/pull/19516) [#19536](https://github.com/emqx/emqx/pull/19536) メトリックの更新と読み取りに必要なルックアップ数を削減しました。受信および送信MQTTパケットメトリックの更新は、各ネームスペース更新グループ内のすべてのカウンターでカウンター参照を再利用します。
  - [#19528](https://github.com/emqx/emqx/pull/19528) `tcp_backend = socket` のTCPリスナーでは、1KBまでのパケットに対して受信システムコール数を減らし、受信QoS 0 PUBLISHパケットあたりのブローカCPUを約7%削減しました。より大きなパケットでは同等かそれ以下です。
  - [#19532](https://github.com/emqx/emqx/pull/19532) SUBACKとUNSUBACKの後、クライアントのテーブルエントリ更新を1回の書き込みで済ませるようにし、新規サブスクライブ接続の高レート時のSUBSCRIBEレイテンシを低減しました。
  - [#19555](https://github.com/emqx/emqx/pull/19555) `mria`を1.0.2にアップグレードしました。クラスタテーブルへの書き込みは、呼び出しプロセスが10件から100件のキュー済みメッセージを持つ場合のみヘルパープロセスで実行されるようになり、新規サブスクリプションの高レート時のSUBSCRIBEレイテンシを低減しました。
  - [#19545](https://github.com/emqx/emqx/pull/19545) リテーナー有効時、ワイルドカードなしのトピックフィルターにクライアントがサブスクライブすると、リテーナーメッセージの配信準備前にリテーナーメッセージの有無をチェックし、該当メッセージがなければそれ以降のリテーナーメッセージ処理を行わずCPU使用率を削減します。

- **サブスクリプション検索と起動**
  - [#19245](https://github.com/emqx/emqx/pull/19245) `emqx ctl subscriptions show <ClientId>` コマンドはノード上のすべてのサブスクリプションをスキャンせずに特定クライアントのサブスクリプションを表示します。
  - [#19183](https://github.com/emqx/emqx/pull/19183) リリースパッケージに含まれる `nodetool` ヘルパーは事前コンパイル済みです。

### バグ修正

#### コアMQTT機能

- [#19489](https://github.com/emqx/emqx/pull/19489) MQTT TCPリスナーのデフォルト `tcp_backend` を `gen_tcp` に戻しました。

  6.3.0でUnix/Linuxのデフォルトが `socket` になりましたが、接続ごとのメモリ使用量が増えるため、対応が完了するまでデフォルトを `gen_tcp` に戻します。メッセージトラフィックのあるテストではまだコストは測定されていません。`socket` バックエンドは引き続き `tcp_backend = socket` で利用可能です。明示的に設定したリスナーは影響を受けません。デフォルトに依存するリスナーはアップグレード時に `gen_tcp` に切り替わり、再起動とアクティブ接続の切断が発生します。

- [#19298](https://github.com/emqx/emqx/pull/19298) 6.3.0で導入された、`socket` バックエンドのTCPリスナーにおける大規模QoS 1メッセージバースト時の高CPU使用率と遅いメッセージ配信のパフォーマンス低下を修正しました。アウトゴーイングメッセージのバッチ処理によりバーストスループットも改善しました。

- [#19326](https://github.com/emqx/emqx/pull/19326) フルインフライトウィンドウを接続混雑シグナルとして扱わないようにメッセージ配信を修正しました。QoS 0メッセージはインフライトウィンドウが満杯でも配信可能となり、不要なキューイングやメッセージドロップを減らしつつ、各トピックとQoSレベルの順序は保持されます。

  また、配信レート制限下でのQoS 1/2メッセージの順序入れ替わりを修正し、キュー済みメッセージが送信前に配信クォータを消費しないようにしました。

- [#19351](https://github.com/emqx/emqx/pull/19351) `esockd` を5.17.4から5.17.8にアップグレードし、以下のリスナー関連問題を修正しました：

  - `socket` バックエンドで小さい `tcp_options.recbuf` 値を使うと高MTUリンクでTCPスループットが著しく低下する問題を修正。
  - PROXY Protocol v2でゼロ長のプロキシ情報を含むヘッダーがMQTTデータを消費し、切断されたIPv4/IPv6アドレス情報をクラッシュなしで拒否する問題を修正。
  - 不完全なPROXY Protocol v1ヘッダーを `socket` バックエンド接続で拒否するように。
  - リスナーオプションのマージとソケットチューニングを修正し、未初期化カウンター更新時のアクセプタークラッシュを防止。

- [#19630](https://github.com/emqx/emqx/pull/19630) `gen_tcp` バックエンドのリスナーで、短時間読み込みを停止したサブスクライバーへのQoS 0配信遅延を修正しました。サブスクライバーが読み込みを再開した後も最大で `mqtt.idle_timeout`（デフォルト15秒）まで配信が停滞する問題がありました。TCP受信バッファが小さいクライアントは接続中ずっと送信されたQoS 0メッセージの一部しか受信できませんでした。混雑した接続はタイマーで送信キューをチェックし、サブスクライバーの読み込み再開後に速やかに配信を再開します。

- [#19144](https://github.com/emqx/emqx/pull/19144) セッションレジストリのクリーンアップ処理が、クライアント切断時に停止する問題を修正しました。切断されたクライアントをスキップして古い登録を削除し続けます。

- [#19316](https://github.com/emqx/emqx/pull/19316) リミッター・レジストリの再起動やノードシャットダウン時にクリーンアップが実行されなかった場合、`persistent_term`にレートリミッターのバケットエントリがリークする問題を修正しました。

#### ゲートウェイ

- [#19422](https://github.com/emqx/emqx/pull/19422) MQTT-SNセッションの引き継ぎが、EMQX 6.3.0、6.3.1、6.3.2へのローリングアップグレード中の混在バージョンクラスターで失敗する問題を修正しました。異なるバージョンのノードで再接続やウェイクアップするとクライアントチャネルが失敗またはクラッシュし、セッション再開や保留メッセージ配信が妨げられていました。

- [#19459](https://github.com/emqx/emqx/pull/19459) MQTT-SNゲートウェイが送信PUBLISHパケットから `DUP` と `RETAIN` フラグを省略する問題を修正しました。これによりクライアントは再送メッセージやサブスクリプション時に配信される保持メッセージを識別可能になりました。

- [#19393](https://github.com/emqx/emqx/pull/19393) セッションを再開したゲートウェイクライアントへのQoS 1/2配信時に毎回エラーログが出る問題を修正しました。

  メッセージキューやストリーム使用時に、フックコールバック内で例外が発生し、EMQXが `hook_callback_exception` をエラーレベルでログ出力していました。配信自体は影響を受けません。MQTT-SNクライアントのスリープからのウェイクアップなど、セッションライフサイクルフックが実行されないゲートウェイチャネルは、コールバックが必要とするチャネルメタデータが設定されていませんでした。

#### アクセス制御

- [#19282](https://github.com/emqx/emqx/pull/19282) `hostname_resolution = dynamic` のHTTP認証で、`Content-Type` ヘッダー名が小文字でないレスポンス（例：`Content-Type: application/json`）を拒否していた問題を修正しました。現在は受け入れられます。以前は認証バックエンドが `unsupported_content_type` を返し、クライアントが接続できませんでした。

#### データ統合

- [#19313](https://github.com/emqx/emqx/pull/19313) HTTPベースのコネクター（HTTPサーバー、GCP PubSub Producer、Couchbase、Snowflakeなど）で応答がない接続の検出を改善しました。

  修正前は、レスポンス待ちのリクエストがある接続は、リクエストタイムアウト（`resource_opts.request_ttl`）＋ `max_inactive` 経過後に再接続されていました。`request_ttl` が大きいと長時間かかり、`request_ttl = infinity` では再接続されませんでした。

  修正後は、リクエスト待ちで60秒間リクエスト送信がない場合、または `max_inactive` がそれ以上の場合は `max_inactive` 後に再接続します。デフォルト設定（`request_ttl` 45秒、`max_inactive` 10秒）は影響を受けません。

  これにより、約50秒以上の `request_ttl` 設定のコネクターの動作が変わります。60秒を超えるレスポンスは再接続で中断される可能性があります。リモートサービスの応答が60秒以上かかる場合は、`max_inactive` を想定最長応答時間以上に設定してください。

#### オブザーバビリティ

- [#19561](https://github.com/emqx/emqx/pull/19561) ログハンドラーで `payload_encode = hidden` を設定した際のログフォーマッタクラッシュを修正しました。以前は、Cluster Linkingの `recv_data` イベントの `data` フィールドのようなtermフィールドを含むデバッグログが `FORMATTER CRASH` レポートに置き換わっていました。現在は `Encoded(hidden)=******` としてマスクされ、通常通りログが書き込まれます。

#### ノードとクラスター

- [#19444](https://github.com/emqx/emqx/pull/19444) CPUクォータ下（例：`docker run --cpus` や Kubernetes CPU制限）でのErlangスケジューラ数を修正しました。

  6.3.0以降、EMQXはホストのCPUコア数分のスケジューラを起動していましたが、コンテナが使用可能なCPU数に合わせていませんでした。スケジューラ間でCPUクォータを奪い合い、同じメッセージレートで約30%多くCPUを消費していました。現在はCPUクォータに合わせた数のスケジューラを起動します。明示的に設定する場合は `node.schedulers` を使用してください。

- [#19160](https://github.com/emqx/emqx/pull/19160) コアノードがクラスターに参加または離脱する際に発生する `mria` アプリケーションのクラッシュを修正しました。

  ```
  Reason: {badarg,[{ets,select,[gproc,[{{{{n,l,{mria_rlog_replica,route_shard_m,'$1'}},n},'$2','_'},[],[{{'$1','$2'}}]]],[{error_info,#{cause => id...
  ```

  この修正で、クラスターメンバー変更時に再起動されるビジネスレベルアプリケーションのリストから `mria` アプリの `gproc` 依存を除外しました。

- [#19578](https://github.com/emqx/emqx/pull/19578) ローリングアップグレード中の避難セッションインポート時のクラッシュを修正しました。セッションが古いEMQXバージョンのノード由来でリスナーメタデータが欠落している場合に発生していました。

- [#19580](https://github.com/emqx/emqx/pull/19580) ローリングアップグレード中にノード避難が完了しない問題を修正しました。

  - **送信元ノードバージョン:** EMQX 5.8〜5.10、6.0.0〜6.0.3、6.1.0〜6.1.4、6.2.0〜6.2.3、6.3.0
  - **宛先ノードバージョン:** EMQX 6.0.4、6.1.5、6.3.1
  - **影響:** 宛先ノードがセッション追い出し呼び出しに応答せず、送信元ノードがクライアントセッションを保持して無限に再試行していました。
  - **解決:** EMQXノードは呼び出しに再度応答し、ノード避難が完了可能になりました。

#### パッケージング

- [#19141](https://github.com/emqx/emqx/pull/19141) Dockerイメージの `/etc/passwd` に `root` エントリを復元し、`docker run --user root` が再び動作するようにしました。6.3.1でイメージがハードニングベースに移行した際に削除され、数値形式の `--user 0:0` のみが動作していました。

## 6.3.1

*リリース日: 2026-09-17*

EMQX 6.3.1にアップグレードする前に破壊的変更を必ずご確認ください。

### 強化点

#### アクセス制御

- [#18777](https://github.com/emqx/emqx/pull/18777) Dashboard JSON APIログインにSCRAM-SHA-256チャレンジレスポンス認証をオプションで追加し、組み込みAPI SpecログインページをデフォルトでSCRAMに切り替えました。既存のパスワードログインはデフォルトで有効です。

  `dashboard.password_login = scram_only` の場合、ユーザー名とパスワードで `POST /api/v5/login` を使うスクリプトやサードパーティクライアントはSCRAMチャレンジレスポンスフローに移行するかAPIキーを使う必要があります。

#### パッケージング

- [#18977](https://github.com/emqx/emqx/pull/18977) 公式EMQX Enterprise DockerリリースイメージをDocker Hardened Debian 13 (Trixie)に切り替えました。ランタイムイメージからは `apt` や `dpkg` などのパッケージマネージャが除去されました。

  リリースイメージにはビルド出所とソフトウェア部品表（SBOM）証明が含まれ、Docker Scoutがハードニングベースイメージの脆弱性評価（VEXステートメント）を適用可能です。

#### パフォーマンス

- [#18806](https://github.com/emqx/emqx/pull/18806) MQTT接続のメモリ使用量を削減しました。

  接続時にレートリミッター状態を割り当てていましたが、レート制限が設定されていない場合も割り当てていました。現在はクライアントが初めてパブリッシュまたはサブスクライブする際に割り当てるため、接続のみの接続は約2KB少ないメモリを使用します。設定済みのレート制限は従来通り動作します。

- [#18807](https://github.com/emqx/emqx/pull/18807) MQTTセッションのメモリ使用量を削減しました。

  配信レート制限が設定されていない場合でも、セッション作成時に配信レートリミッター状態を割り当てていました。現在は配信レート制限が設定されてから最初の配信時に割り当てるため、セッションごとに約0.5KB節約します。設定済みの配信レート制限は従来通り動作します。

- [#18808](https://github.com/emqx/emqx/pull/18808) パブリッシュまたはサブスクライブするMQTT接続のメモリ使用量を削減しました。

  接続ごとのレートリミッター状態は、実際に設定されたレート制限のみ割り当てます。デフォルト設定（レート制限なし）ではアクティブ接続で約1.6KB少ないメモリを使用します。設定済みのレート制限は従来通り動作し、ランタイム追加も含みます。

- [#18809](https://github.com/emqx/emqx/pull/18809) レート制限が設定されたMQTT接続のメモリ使用量を削減しました。

  すべての接続で共有していたレートリミッターの管理情報を個々の接続にコピーしなくなり、レート制限有効時に接続ごとに約0.5KB節約します。レート制限の動作は変更ありません。

- [#18875](https://github.com/emqx/emqx/pull/18875) マルチテナントネームスペースに属するMQTT接続のメモリ使用量を削減しました。

  テナントクライアントのレートリミッター状態は、クライアントが初めてパブリッシュ、サブスクライブ、またはメッセージ受信する際に割り当て、実際に設定された制限のみ割り当てます。通常接続と同様の動作です。設定済みのテナントおよびクライアントレート制限は従来通り動作します。ネームスペースのリミッター設定が削除された場合、以降のリミッター検査は操作を拒否し続けます。
