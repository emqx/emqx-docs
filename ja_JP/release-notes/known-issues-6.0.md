# EMQX 6.0 の既知の問題

## 6.0.0

| バージョン     | 問題                                                         | 回避策                                                       | ステータス |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ---------- |
| 6.0.0         | **古いブリッジが設定に存在する場合、5.x から 6.0.0 へのクラスターのローリングアップグレードができない**<br />古い EMQX バージョンで起動されたクラスターで、現在は非推奨となった `bridges` 設定ルートが含まれている場合、新しい 6.0 ノードはこれらのルートを廃止しているため、設定の同期に失敗し、対応するコネクター、アクション、ソースが起動できません。 | 6.0.1 以降では、古いノードに対して RPC コールを行い、`bridges` を `connectors`、`sources`、`actions` に変換する設定アップグレードを実施するため、手動介入を減らしたローリングアップグレードが可能です。<br />または、影響を受ける各ブリッジを HTTP API または CLI 経由で更新（例：説明文の変更）することで設定更新を誘発し、永続化された `cluster.hocon` ファイルもアップグレードされます。<br />以下のコネクター／ソース／アクションはローリングアップグレード前に手動での変更が必要な場合があります：<br /> - GCP PubSub Consumer<br /> - Kafka Consumer<br />設定内にまだ `topic_mapping` フィールドが含まれるソースがある場合は、そのフィールドを設定から削除し、エントリーごとに「ソース＋ルール」ペアを作成してください。 |            |
| 5.1.0         | **クラスターに新しいコアノードを追加するとレプリカントノードが起動時にハングする可能性がある**<br />クラスター変更で新しいコアノードを追加する際、追加されたコアがレプリケーション関連のプロセスを起動できず、アップグレードまたは新規追加されたレプリカントノードの起動がハングすることがあります。<br />Kubernetes 環境では、レプリカントポッドのレディネスプローブ失敗によりコントローラーが再起動を繰り返す原因となりました。<br />この問題は、例えば既存の 2 コア＋2 レプリカントクラスターに対して、新しい EMQX バージョンのコアノードとレプリカントノードをそれぞれ 2 台ずつ追加するアップグレードロールアウト時に発生しやすいです。 | (再)デプロイ後にレプリカントノードが起動時にハングする場合は、新しく追加されたコアノードを1台ずつ強制的に再起動し、レプリカントの起動が完了するまで繰り返してください。 | 6.0.1 で修正 |
| 5.7.0         | **クラスターリンクのガベージコレクションがアクティブルートを誤って削除する可能性がある**<br />複数の独立したクラスターリンクを設定し、一部のリンクが長期間ダウンしている場合、ガベージコレクション処理が内部ルーティングテーブルからアクティブルートを誤って削除することがあります。これにより、影響を受けたクラスターリンクはメッセージの一部のみを転送するか、転送を完全に停止する可能性があります。 | -                                                            |            |
