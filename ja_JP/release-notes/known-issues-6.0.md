# EMQX 6.0 の既知の問題

## 6.0.0

| バージョン | 問題                                                         | 回避策                                                       | ステータス |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ---------- |
| 6.0.0       | **古いブリッジが設定に含まれている場合、5.x から 6.0.0 へのクラスターのローリングアップグレードができない**<br />旧バージョンの EMQX から起動しているクラスターで、現在は非推奨となった `bridges` 設定ルートが含まれている場合、新しい 6.0 ノードに設定を同期できず、該当するコネクター、アクション、ソースが起動に失敗します。 | 6.0.1 以降では、古いノードに RPC コールを送り、`bridges` を `connectors`、`sources`、`actions` に変換する設定アップグレードを行うため、手動介入を減らしたローリングアップグレードが可能です。<br />または、HTTP API または CLI を使って影響を受ける各ブリッジの設定を更新（例：説明文の変更）することで、永続化された `cluster.hocon` ファイルもアップグレードされます。<br />以下のコネクター／ソース／アクションは、ローリングアップグレード前に手動での変更が必要な場合があります：<br /> - GCP PubSub Consumer<br /> - Kafka Consumer<br />設定内にまだ `topic_mapping` フィールドを含むソースがある場合は、設定から該当フィールドを削除し、エントリごとに「ソース＋ルール」ペアを作成してください。 |            |
| 5.1.0       | **新しいコアノードをクラスターに追加した際、レプリカントノードが起動時にハングする場合がある**<br />クラスター変更で新しいコアノードを追加すると、追加されたコアがレプリケーション関連プロセスの起動に失敗することがあり、その結果、アップグレード済みまたは新規のレプリカントノードが起動時にハングすることがありました。<br />Kubernetes 環境では、レプリカントの Readiness プローブ失敗によりコントローラーがレプリカント Pod を繰り返し再起動する問題が発生しました。<br />この問題は、例えば既存の 2 コア＋2 レプリカントクラスターに新たに 2 コアと 2 レプリカントを追加し、より新しい EMQX バージョンで動作させるアップグレード時に発生しやすいです。 | レプリカントノードが起動時にハングした場合は、新たに追加されたコアノードを一つずつ強制再起動し、レプリカントの起動が完了するまで繰り返してください。 | 6.0.1 で修正 |
| 5.7.0       | **クラスターリンクのガベージコレクションがアクティブルートを誤って削除する場合がある**<br />複数の独立したクラスターリンクが設定され、一部のリンクが長期間ダウンしている場合、ガベージコレクションが内部ルーティングテーブルからアクティブルートを誤って削除することがあります。これにより、該当するクラスターリンクがメッセージの一部のみを転送するか、転送を完全に停止する可能性があります。 | -                                                            | 6.1.0 で修正 |
