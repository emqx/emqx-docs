# EMQX 6.0 の既知の問題

## 6.0.0

| バージョン | 問題                                                         | 回避策                                                       | ステータス |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ---------- |
| 6.0.0       | **古いブリッジが設定にある場合、5.x から 6.0.0 へのクラスターのローリングアップグレードができない**<br />古い EMQX バージョンから起動しているクラスターで、現在非推奨となった `bridges` 設定ルートを含む場合、新しい 6.0 ノードはこれらのルートを廃止しているため、対応するコネクター、アクション、ソースの起動に失敗し、設定同期に失敗します。 | 6.0.1 以降では、古いノードに対して RPC コールを行い、`bridges` を `connectors`、`sources`、`actions` に変換して設定をアップグレードし、手動介入を減らしたローリングアップグレードを可能にしています。<br />または、影響を受ける各ブリッジを HTTP API または CLI で更新（例：説明の変更）し、設定の更新を促すことで、永続化された `cluster.hocon` ファイルもアップグレードされます。<br />以下のコネクター／ソース／アクションは、ローリングアップグレード前に手動での変更が必要な場合があります：<br /> - GCP PubSub Consumer<br /> - Kafka Consumer<br />設定内にまだ `topic_mapping` フィールドを含むソースがある場合は、そのフィールドを設定から削除し、エントリごとに「ソース＋ルール」のペアを作成する必要があります。 |            |
| 5.1.0       | **新しいコアノードをクラスターに追加するとレプリカントノードが起動時にハングする場合がある**<br />クラスター変更で新しいコアノードを追加すると、追加されたコアがレプリケーション関連プロセスの起動に失敗することがあり、その結果、アップグレードまたは新規追加されたレプリカントノードが起動時にハングしました。<br />Kubernetes 環境では、レプリカントのレディネスプローブが失敗し、コントローラーがレプリカントポッドを繰り返し再起動する原因となりました。<br />この問題は、例えば既存の 2 コア＋2 レプリカントクラスターを、より新しい EMQX バージョンで動作する 2 つの新しいコアノードと 2 つの新しいレプリカントに拡張するアップグレードロールアウト時に発生しやすいです。 | レプリカントノードが起動時にハングした場合は、新規追加されたコアノードを一つずつ強制再起動し、レプリカントの起動が完了するまで繰り返してください。 | 6.0.1 で修正 |
| 5.7.0       | **クラスターリンクのガベージコレクションがアクティブルートを削除する場合がある**<br />複数の独立したクラスターリンクを設定し、一部のリンクが比較的長期間ダウンしていると、ガベージコレクション処理が誤って内部ルーティングテーブルからアクティブルートを削除することがあります。これにより、影響を受けたクラスターリンクはメッセージの一部のみを転送するか、メッセージの転送を完全に停止する可能性があります。 | -                                                            | 6.1.0 で修正 |
