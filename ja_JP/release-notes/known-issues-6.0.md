# EMQX 6.0 の既知の問題

## 6.0.4

| バージョン | 問題 | 回避策 | ステータス |
| --------- | ---- | ------ | ---------- |
| 6.0.1 | **アック（ACK）が無効な場合の Kafka および Confluent パブリッシャーアクションにおけるメモリ増加**<br />`parameters.required_acks = none` のとき、Kafka のパブリッシュ要求ごとにパブリッシャーのメモリ使用量が増加し、バッファが消費された後も蓄積されたメモリが解放されません。この問題は EMQX 6.0.1～6.0.4、6.1.0～6.1.5、6.2.0～6.2.3、6.3.0～6.3.2 に影響します。 | すべてのバッファ済みメッセージが送信されるまで待機し、その後アクションの `parameters.required_acks` を `leader_only` または `all_isr` に設定してください。この設定変更によりパブリッシャーが再作成され、蓄積されたメモリが解放されます。 | 6.3.3 で解決済み。詳細は [emqx/emqx#19992](https://github.com/emqx/emqx/pull/19992) を参照してください。 |

## 6.0.0

| バージョン | 問題 | 回避策 | ステータス |
| --------- | ---- | ------ | ---------- |
| 6.0.0 | **古いブリッジが設定に含まれている場合、5.x クラスターから 6.0.0 へのローリングアップグレードができない**<br />以前の EMQX バージョンで起動したクラスターに存在する、現在は非推奨となった `bridges` 設定ルートがあると、新しい 6.0 ノードに設定が同期されず、対応するコネクター、アクション、ソースが起動に失敗します。 | 6.0.1 以降では、古いノードに対して RPC コールを行い、`bridges` を `connectors`、`sources`、`actions` に変換する設定アップグレードを自動で実施し、手動介入を減らしたローリングアップグレードを可能にしています。<br />または、影響を受ける各ブリッジを HTTP API または CLI で更新（例：説明の変更）して設定更新を促すことでも、永続化された `cluster.hocon` ファイルのアップグレードが行われます。<br />以下のコネクター／ソース／アクションは、ローリングアップグレード前に手動での変更が必要な場合があります。<br /> - GCP PubSub Consumer<br /> - Kafka Consumer<br />設定に `topic_mapping` フィールドを含むソースがある場合は、設定から該当フィールドを削除し、各エントリごとに「ソース＋ルール」のペアを作成してください。 |  |
| 5.1.0 | **新しいコアノード追加時にレプリカントノードが起動でハングする可能性がある**<br />クラスター変更で新しいコアノードを追加する際、新規追加されたコアがレプリカントノードに必要なレプリケーション関連プロセスの起動に失敗することがありました。これによりアップグレード済みまたは新規追加されたレプリカントノードが起動時にハングし、Kubernetes 環境ではレプリカントポッドのレディネスプローブ失敗による再起動が繰り返されました。<br />この問題は、例えば既存の 2 コア＋2 レプリカントクラスターに対し、2 つの新しいコアノードと 2 つの新しいレプリカントを追加して新しい EMQX バージョンで展開するアップグレードロールアウト時に発生しやすいです。 | (再)デプロイ後にレプリカントノードがハングした場合は、新規追加されたコアノードを一つずつ強制再起動し、レプリカントの起動が完了するまで繰り返してください。 | 6.0.1 で修正済み |
| 5.7.0 | **クラスターリンクのガベージコレクションがアクティブルートを削除する可能性がある**<br />複数の独立したクラスターリンクを設定し、一部のリンクが長期間ダウンしている場合、ガベージコレクション処理が誤って内部ルーティングテーブルからアクティブルートを削除することがあります。これにより該当クラスターリンクがメッセージの一部のみを転送するか、転送を完全に停止する可能性があります。 | - |  |
