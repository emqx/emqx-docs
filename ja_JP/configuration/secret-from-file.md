# ファイルからシークレットを読み込む

EMQX の多くの設定項目は機密情報を保持します。SSL リスナの鍵パスフレーズ、ブリッジ/コネクタのパスワード、OIDC クライアントシークレット、S3 シークレットアクセスキー、API キーなどです。これらの値を `emqx.conf` や API リクエストに直接埋め込まないために、EMQX はシークレット型のフィールドに対して `file://` URL プレフィックスをサポートしています。EMQX は起動時と設定リロード時に指定されたファイルからシークレットを読み込みます。

## 構文

シークレット型（またはダッシュボードのツールチップに `file://` オプションが明記されている）フィールドでは、以下の形式を使用できます。

```bash
file://<ファイルパス>
```

パスは絶対パスでも、EMQX の作業ディレクトリからの相対パスでもかまいません。ファイルの内容全体がシークレット値として使用されますが、次の変換が行われます。

- **末尾の空白文字は除去されます。** 末尾の改行、復帰、スペース、タブが取り除かれます。先頭および中間の内容はそのまま使用されます。

例:

```bash
# SSL リスナの鍵パスフレーズをファイルから読み込む
listeners.ssl.default.ssl_options.password = "file://etc/certs/key-passphrase"

# MQTT ブリッジのパスワードをファイルから読み込む
bridges.mqtt.upstream.password = "file:///run/secrets/upstream-mqtt-password"
```

## クラスタ構成における注意事項

EMQX をクラスタで運用する場合、設定を読み込むすべてのノードがファイルパスを解決できる必要があります。

- ファイルは設定を読み込む **すべての EMQX ノードに存在しなければなりません**。同じパスでもノードごとのローカルファイルを参照します。EMQX はノード間でファイルをコピーしません。
- 各ノードのファイル内容は一致させてください。一致しない場合、同じ設定項目でもノードごとに異なるシークレット値となります。
- ダッシュボードや REST API から設定を変更すると、`file://...` の文字列がクラスタ全体に伝播し、各ノードがそれぞれローカルのファイルを開きます。

一般的な運用パターンは、EMQX が起動する前に Kubernetes Secrets、Ansible、構成管理ツールなどを使って、すべてのノードに同じパスでシークレットファイルを配置することです。

## 適用範囲

`file://` 構文は、設定スキーマがシークレット型を使用しているすべてのフィールドで利用できます。代表的な例:

- **SSL/TLS リスナ** —— `listeners.<type>.<name>.ssl_options.password`（鍵パスフレーズ）。詳細は [SSL/TLS の有効化](../network/emqx-mqtt-tls.md) を参照してください。
- **ブリッジおよびコネクタ** —— パスワード、API キー、シークレットアクセスキー、JWT トークンなど。
- **クラスタリンク** —— `cluster.links[].password`。
- **ダッシュボード SSO（OIDC）** —— `dashboard.sso.oidc.secret`。
- **ライセンス** —— `license.key`（ライセンス文字列そのもの）。詳細は [ライセンス設定](./license.md) を参照してください。
- **AI Completion** —— `ai.completion_profile.api_key`。

特定のフィールドが `file://` をサポートしているかどうかは、フィールドのダッシュボードツールチップまたは本ドキュメントに明示されます。

## ログとマスキング

EMQX はログおよび HTTP API 応答からシークレット値をマスキングします。シークレットが `file://...` URL で設定されている場合、EMQX はパスそのものをログに出力し、ファイルの内容はログに出力しません。これによって、ノードがどのファイルを読み込んでいるかを運用担当者が確認できます。ファイルから抽出された実際のシークレット値はどのログにも記録されません。

## `file://` を使うべきでない場合

設定フィールドが通常の `string` 型（シークレット型ではない）の場合、`file://` を付けても文字列リテラルとして扱われ、ファイル参照とはみなされません。使用前に各フィールドのスキーマ型が `file://` をサポートしているか確認してください。
